# 外部技能包引入与整合

覆盖：从 GitHub 等其他来源把工具/技能安全纳入 packs 并确认可用，或把整合同类技能进已有包。

## 一、选包与下载

- GitHub 搜索优选取：有正式 release tag、近期有提交、issue 有回应的仓库。
- 选 2-3 个**互补**的仓库（架构、工具链、方法论各有所长），避免同质源；逐个 clone 到 /tmp 审阅，记录各自结构与独有贡献点。
- 下载 release zip 到本地；**不直接执行来源不明的安装脚本**。

## 二、许可核对（先于一切改写）

1. 每个源确认许可（LICENSE 文件 / README 声明）；
2. 取**最严格**的许可作为整合版许可（如三源中 CC BY-NC-SA 4.0 最严，则全包用该许可）；
3. 在包内 README 附"来源-许可-贡献"对照表，引入处标注出处。

## 三、审查（安装前必做）

1. `SKILL.md` 存在且 frontmatter（name/description）合法；
2. 脚本内容无危险操作（递归删除、数据外传、混淆代码）；
3. 依赖清单明确、可审计。
- 审查不合格直接丢弃，不进入下一步。

## 四、验收（带外部 CLI 依赖的技能包必须）

1. 按官方文档安装依赖；
2. 对照官方文档核验每个命令面；
3. 最小项目冒烟测试（跑通一个真实小任务）；
4. 归档推送（packs 随 pi-backup 同步）。

## 五、本地摸底与三层归置

1. 通读 `packs/` 现有技能与 `packs/README.md` 索引，标出功能重叠项；
2. **通用能力**（≥2 个技能可复用）：提取到共享位置（lib/ 或通用技能）；
3. **专用能力**：按领域分类存放为独立技能目录；
4. **繁重/不常用功能**（重依赖、需外部服务、低频）：不落地实现，只在 README 待办区记录来源与用途。

## 六、整合纪律

- 与现有技能或远程更新整合以**合并优化为主，禁止直接覆盖**（本地是超集：中文说明、pi 工具适配、缓存友好改造、EXPERIENCE.md 经验都保留）。
- 远程更新：拉取到临时目录 → `diff -r` 对照 → 本地未改动的增量合入，本地改过的以本地为准手工合并。
- 命名平实化：去修辞化命名（天命/法典/铁律等），保留同一执行语义。
- 参数可配置：上游写死的常数收敛为"可调参数"表，标注默认值。
- 补强工程层：上游往往只讲初始化不讲长期使用——补 engineering.md/templates/README。

## 七、收尾

- 更新 `packs/README.md` 索引与技能 frontmatter（name/description，不带时间戳，1-2 句）。
- 记录整合说明：来源、纳入/未纳入项及原因；有长期价值的结论 memory_store 入库。
