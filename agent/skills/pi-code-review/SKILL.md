# pi-code-review 代码审查

审查代码时的标准流程：**自检 → 确定性检查脚本 → 人工检查清单 → 分级报告**。

## 工作流

### 第 0 步：技能自检（使用前必做）

`bash ~/.pi/agent/skills/pi-code-review/review.sh --selfcheck`

检查两项：
1. **本仓库技能更新**：对比远程仓库中技能文件是否有新提交（有则先 `git pull` 再用，避免用过时版本）
2. **参考项目更新**：`alibaba/open-code-review`（阿里云开源代码审查引擎）最新 release 是否高于技能基线版本（frontmatter `参考基线`）——有则查看其 releases 确认是否需要吸收新能力（审查维度、规则、模式）后更新技能

**更新检查节流**（2026-08-15 新增）：上次远程检查时间记录在 `~/.pi/logs/pi-code-review-selfcheck.ts`（运行时数据，不入库）。距上次检查不足 7 天时跳过远程查询（git fetch + GitHub API 每次 ~5-15s），输出上次检查时间；`--selfcheck --force` 强制重新检查并刷新时间戳。

自检未通过（技能有更新但未拉取）时先同步再继续。

### 第 1 步：确定审查范围

| 场景 | 命令 |
|------|------|
| git 仓库内的改动（默认，审查 HEAD + 未跟踪文件） | `bash ~/.pi/agent/skills/pi-code-review/review.sh` |
| 指定目录全量扫描（无需 git） | `bash ~/.pi/agent/skills/pi-code-review/review.sh --all <dir>` |
| 查看用法 | `bash ~/.pi/agent/skills/pi-code-review/review.sh --help` |

**意图对齐（Spec 轴，参考 mattpocock/code-review 双轴法）**：先明确变更的「发起意图」——issue/用户需求/commit message 中的原始诉求，一句话写出来。逐文件核对时回答两个独立问题：改动**是否实现该意图**（Spec 轴）？是否符合仓库标准（Standards 轴 = 本清单）？大 diff 时两轴可用 subagent 并行审查再汇总，避免互相污染上下文。

### 第 2 步：运行确定性检查

运行 `review.sh` 获取：git 卫生（空白错误/密钥扫描/大文件）、语法检查（JS/Python/Shell/JSON/YAML）、可疑模式标记、可用的测试命令清单。

**要点**：
- 脚本只检测不执行、不修改任何文件。
- 阶段 D 检测出的测试/typecheck 命令**由你自行决定运行**（改动前必跑测试，见第 4 步）。
- 密钥扫描结果已脱敏，只显示位置；**禁止**输出密钥原文。

### 第 3 步：人工检查清单（逐项核对，每项输出结论）

不要只看 diff 表面，对每个变更文件逐项核对：

1. **正确性**
   - 分支是否覆盖边界值、空值、null/undefined、空数组/空字符串
   - 错误处理路径：异常是否被捕获并给出有用信息，失败时是否回滚
   - 类型转换陷阱：字符串/数字隐式转换、NaN、精度（浮点/大数）
   - 循环边界：off-by-one、无限循环、死循环风险

2. **安全**
   - 输入校验：用户输入是否经过校验/清洗（SQL 注入、命令注入、XSS）
   - 鉴权/授权：新接口是否缺失权限检查；越权访问风险
   - 硬编码密钥、密钥落盘、日志中泄露敏感信息
   - 路径穿越：拼接用户输入的文件路径是否被消毒

3. **资源**
   - 文件句柄/网络连接/数据库连接是否关闭（try/finally）
   - 超时设置：外部调用是否有超时，超时后行为是否正确
   - 大循环/递归深度：是否存在内存或 CPU 风险

4. **并发与状态**
   - 共享可变状态：竞态条件、重复执行副作用
   - 异步：回调/promise/await 是否遗漏或错误串联

5. **回归影响**
   - 被修改 API/函数的所有调用方是否受影响（用 grep 搜调用处）
   - 配置、环境变量、依赖版本变更的影响面

6. **可维护性**
   - 死代码、重复逻辑、未使用变量/导入
   - 命名是否反映意图；注释是否与实现一致（过时注释）

### 第 4 步：验证要求

- **改动前**：先运行 `review.sh` 阶段 D 检测出的测试命令，确认基线通过。
- **改动后**：重跑相关测试 + 类型检查（tsconfig 存在时 `npx tsc --noEmit`）+ lint。
- 对边界场景（空值、超限、断网、并发）列出需要人工测试的步骤。

### 第 5 步：分级报告

报告格式（每个问题带 `文件:行号`）：

```
## 代码审查结果
**审查文件数**: N | **问题**: X HIGH / Y MEDIUM / Z LOW

### HIGH（必须修）
- `路径:行号` — 问题描述
  > 修复建议: ...

### MEDIUM（建议修）
- `路径:行号` — 问题描述
  > 修复建议: ...

### LOW（可选）
- `路径:行号` — 问题描述
```

**分级标准**：
- **HIGH**：明确的 bug、安全问题、会导致功能错误
- **MEDIUM**：边界情况、健壮性、性能、风格，依赖上下文
- **LOW**：疑似误报、缺乏上下文、吹毛求疵

无问题时明确说明："审查完成，N 个文件未发现问题。"

**双轴结论**（报告必含）：`Standards 符合度：X/N 项违规 | Spec 满足度：改动是否实现发起意图（是/部分/否，附一句依据）`。两轴结论独立，互不替代。

## 约定

- **只读**：审查过程不改任何文件。用户明确要求"修复"后才动手，且修复前列出计划。
- **敏感信息脱敏**：报告密钥/凭据时只报位置，不显示内容。
- **不确定的先验证**：对可疑点用 grep/阅读代码确认，不凭空猜测。
- **测试先行**：审查涉及的功能改动，必须确认测试已运行并通过后再报告完成。
