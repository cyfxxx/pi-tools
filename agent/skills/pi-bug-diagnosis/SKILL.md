# pi-bug-diagnosis 技能

硬 bug 诊断纪律。仅在明确论证时才能跳过阶段（如：回路无法构建时按"无法建回路"分支处理，而不是跳去猜）。

开始前：检索记忆库（memory_search）与 `~/.pi/docs/` 既有文档建立相关模块心智模型；涉及密钥时先脱敏。

## 阶段 0：脱敏

本技能要求展示命令、输出与捕获产物。**先脱敏所有秘密**：用 `<REDACTED>` 替代。回路对 env var 构建，让凭据留在环境里而非展示内容中。捕获产物携带 auth 头时只引用携带信号的几行。

脱敏后不足以诊断时，明确说出来并询问用户。

## 阶段 1：构建反馈回路

**这是本技能的核心。** 其余都是机械动作。如果你有该 bug 的**紧**通过/失败信号（能在_这个_ bug 上变红），你就能找到根因；二分、假设检验、插桩都只是消费它。没有它，盯着代码看再多也没用。

在此投入不成比例的努力。**要激进、要有创造性、拒绝放弃。**

### 构建回路的方式（大致按此顺序）

1. **失败测试**：到达 bug 的任何 seam（单元/集成/e2e）。
2. **curl / HTTP 脚本**：对运行中的 dev server。
3. **CLI 调用**：用 fixture 输入，stdout 与已知良好快照 diff。
4. **无头浏览器脚本**：browser 工具（navigate/click/extract/evaluate）驱动 UI，断言 DOM/console/network。
5. **重放捕获的 trace**：把真实网络请求/负载/事件日志存盘，隔离回放。
6. **一次性 harness**：最小系统子集（单服务 + mock 依赖），单函数调用触发 bug 路径。
7. **属性/模糊循环**：bug 是"偶尔输出错"时，跑 1000 个随机输入找失败模式。
8. **二分 harness**：bug 出现在两个已知状态之间（commit/数据集/版本）时，自动化"在状态 X 启动、检查、重复"，供 `git bisect run`。
9. **差分循环**：同一输入跑旧版 vs 新版（或两种配置）diff 输出。
10. **人工介入脚本**：最后手段。必须人点击时，用脚本驱动_他们_，让回路仍然结构化。输出回馈给你。

回路建对了，bug 就解决了 90%。

### 收紧回路

把回路当产品对待。有_一个_回路后继续**收紧**：

- 能更快吗？（缓存 setup、跳过无关初始化、缩小测试范围）
- 信号更锐利吗？（断言具体症状，而非"没崩溃"）
- 更确定吗？（固定时间、seed RNG、隔离文件系统、冻结网络）

30 秒的 flaky 回路跟没有差不多；2 秒确定性的回路是调试超能力。

### 非确定性 bug

目标不是干净复现而是**更高复现率**。触发 100 次、并行化、加压、收窄时间窗、注入 sleep。50% 的 flake 可调试；1% 不可，持续提高复现率到可调试为止。

### 确实无法建回路时

停下并明确说明。列出尝试过什么。向用户要：(a) 能复现的环境访问权，(b) 脱敏的捕获产物（HAR/日志转储/core dump/带时间戳的录屏），或 (c) 临时生产插桩许可。**没有回路就不要进入假设阶段。**

### 完成标准：紧且能变红的回路

阶段 1 完成标准——你能说出**一条命令**（脚本路径/测试调用/curl），且**已实际运行至少一次**（展示调用与输出，已脱敏），并且：

- [ ] **能变红**：驱动真实 bug 代码路径，断言**用户的精确症状**，能对此 bug 变红、修复后变绿。不是"运行无错"，必须能_抓住这个具体 bug_
- [ ] **确定性**：每次运行同样结论（flaky：固定高复现率，如上）
- [ ] **快速**：秒级而非分钟级
- [ ] **agent 可跑**：可无人值守运行；人只在交互回路中

如果发现自己先读代码构建理论而这条命令还不存在：**停。直接跳假设正是本技能要防止的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：重现 + 最小化

跑回路，看着它变红。

确认：

- [ ] 回路产生的是**用户描述**的失败模式，不是附近恰好发生的另一个失败。错 bug = 错修复
- [ ] 多次运行可复现（非确定性 bug 则以足够调试的高频率复现）
- [ ] 已捕获精确症状（错误消息/错误输出/慢的时序），后续阶段可据此验证修复

### 最小化

变红后，把复现缩小到**仍能变红的最小场景**。一次一处地裁剪输入、调用方、配置、数据、步骤，每次裁剪后重跑回路，只保留对失败承重的部分。

目的：最小复现缩小阶段 3 的假设空间（可怀疑的部件更少），并成为阶段 5 的干净回归测试。

完成标准：**每个保留元素都承重**——移除任何一个都会让回路变绿。

未复现且未最小化，不得继续。

## 阶段 3：假设

测试任何假设前先产出 **3–5 个排序假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：陈述它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会加重。"

无法陈述预测的假设是空想：丢弃或磨尖它。

**测试前把排序清单给用户看。** 用户常有一句话重排的知识（"我们刚部署过 #3"），或知道已排除的假设。便宜检查点，大省时。不阻塞：用户不在就按你的排序继续。

## 阶段 4：插桩

每个探针必须对应阶段 3 的某个预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**（环境支持时）。一个断点胜过十条日志
2. **定向日志**：在能区分假设的边界处
3. 绝不"全量打日志再 grep"

**每条调试日志打唯一前缀**，如 `[DEBUG-a4f2]`。清理时一次 grep 即可。无标签的日志存活；带标签的日志必死。

**性能分支**：性能回退用日志通常是错的。改为：先建基线测量（计时 harness、performance.now、profiler、query plan），再二分。**先测量，后修复。**

## 阶段 5：修复 + 回归测试

**修复前**先写回归测试，但仅当存在**正确 seam** 时。

正确 seam：测试在调用点如真实 bug 模式发生处演练。如果唯一可用的 seam 太浅（单调用者测试而 bug 需要多调用者；单测无法复现触发链），那里的回归测试给的是虚假信心。

**没有正确 seam 本身就是发现。** 记下它：架构阻止了 bug 被锁死。把这一点标记给后续阶段（如：提交信息/记忆库中说明需要架构调整）。

有正确 seam 时：

1. 在 seam 处把最小复现变成失败测试
2. 看它失败
3. 应用修复
4. 看它通过
5. 对原始（未最小化）场景重跑阶段 1 的回路

## 阶段 6：清理

宣布完成前必须：

- [ ] 原始复现不再复现（重跑阶段 1 回路）
- [ ] 回归测试通过（或已文档化 seam 缺失）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀确认）
- [ ] 一次性原型已删除（或移到明确标注的调试位置）
- [ ] 正确的假设陈述在提交信息里，让下一个调试者受益
- [ ] **沉淀记忆**：memory_store 存入解决方案（根因/回路形态/正确 seam），跨会话复用

## 约定

- 阶段顺序不可跳：回路 → 重现最小化 → 假设 → 插桩 → 修复回归 → 清理
- 回路优先：没有能变红的命令，任何假设都是赌博
- 一次一个变量：插桩与修复都遵守
- 脱敏：所有展示内容先 REDACTED
