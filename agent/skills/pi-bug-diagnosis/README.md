# pi-bug-diagnosis 技能

硬 bug 诊断纪律。仅在明确论证时才能跳过阶段（如：回路无法构建时按"无法建回路"分支处理，而不是跳去猜）。

## 工作流

```
脱敏 → 构建反馈回路 → 重现+最小化 → 假设 → 插桩 → 修复+回归测试 → 清理
```

## 快速开始

```bash
# 1. 脱敏
# 将敏感信息替换为 <REDACTED>

# 2. 构建反馈回路
# 创建能变红的测试/脚本

# 3. 重现 + 最小化
# 跑回路，确认失败
# 裁剪到最小复现

# 4. 假设
# 产出 3-5 个排序假设
# 给用户看排序清单

# 5. 插桩
# 一次只改一个变量
# 每条日志打唯一前缀

# 6. 修复 + 回归测试
# 先写回归测试
# 应用修复
# 重跑回路

# 7. 清理
# 移除所有插桩
# 沉淀记忆
```

---

## 约定

- **阶段顺序不可跳**：回路 → 重现最小化 → 假设 → 插桩 → 修复回归 → 清理
- **回路优先**：没有能变红的命令，任何假设都是赌博
- **一次一个变量**：插桩与修复都遵守
- **脱敏**：所有展示内容先 REDACTED

## 常见问题

- **Q1**: 如何判断回路是否合格？
  **A**: 能变红、确定性、快速、agent 可跑。

- **Q2**: 非确定性 bug 怎么办？
  **A**: 目标是更高复现率，不是干净复现。触发 100 次、并行化、加压。

- **Q3**: 确实无法建回路时怎么办？
  **A**: 停下并明确说明。向用户要环境访问权或捕获产物。

- **Q4**: 性能回退怎么诊断？
  **A**: 先建基线测量，再二分。**先测量，后修复。**
